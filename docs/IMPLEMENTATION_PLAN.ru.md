# План развития HDT Collection Exporter

Дата: 3 октября 2026 года.

## Цель и границы

Реализовать все предложенные улучшения: публичный x64-релиз, корректное сравнение коллекций разных аккаунтов, надёжное хранение файлов, один плагин с выбором языка, понятный интерфейс и результат экспорта, тесты и CI, сводку коллекции и историю снимков с выбором даты сравнения.

Основная платформа — установленный Windows HDT. Плагин остаётся WPF/.NET Framework 4.7.2/x64. Данные по-прежнему считываются через HDT и сохраняются локально. Работа с сайтом ограничена совместимостью его импорта; изменения Swift-адаптера обеспечивают согласованную семантику экспорта.

Предлагаемые выпуски:

| Выпуск | Содержание |
| --- | --- |
| 1.4.2 | Проверенная публичная x64-сборка, исправленные инструкции и базовая автоматическая проверка сборки. |
| 1.5.0 | Полные снимки по аккаунтам, миграция и надёжная запись; один плагин, выбор языка, новый основной экран, состояние коллекции, предварительная сводка изменений и удобный результат экспорта. |
| 1.6.0 | История снимков, сравнение с выбранной датой, сводка по наборам и редкости. |

Номера версий — предложение для реализации. Каждый выпуск должен иметь собственные критерии готовности и проверенный набор файлов.

## 1. Закрепить совместимость и выпустить x64-исправление

Затрагиваемые области: `build.ps1`, проект и решение, `Properties/AssemblyInfo.cs`, версия в точке входа плагина, инструкции, release notes и `.github/workflows`.

Работы:

- Зафиксировать текущий JSON-контракт версии 3 и CSV-заголовки на существующих примерах Windows и HSTracker.
- Добавить Windows CI: сборка Release и Debug/x64, проверка архитектуры DLL, создание экземпляров обеих существующих точек входа и их окон.
- Получать зависимости сборки из закреплённого официального архива HDT с проверкой контрольной суммы. Не использовать автоматически меняющийся `latest` для воспроизводимой сборки.
- Поддержать переносимые reference assemblies 4.7.2 и явный выбор пути сборки, чтобы CI мог проверить штатный и резервный варианты.
- Улучшить поиск HDT: сначала явно переданная папка, затем путь работающего HDT и известные места установки. Учитывать нестандартную установку на другом диске.
- В резервной сборке проверять результаты каждого шага и свежесть сгенерированных WPF-файлов. Не принимать старые файлы из obj за результат неудачной сборки.
- Синхронизировать версию DLL, версию IPlugin, архив и документацию; подготовить release notes и SHA256.
- Выпустить DLL и ZIP с инструкциями. Сохранить прежние опубликованные версии для отката.

Готово, когда скачанная именно из нового GitHub Release DLL имеет AMD64-архитектуру, загружается в HDT и открывает окно без BadImageFormatException. Проверка только локальной сборки недостаточна.

## 2. Отделить полное состояние коллекции от формата экспорта

Затрагиваемые области: `HdtCollectionProvider`, `CollectionSnapshot`, `CollectionExportService`, `ExportOptions` и модели внутреннего хранения.

Работы:

- Всегда читать полные количества normal, golden, diamond, signature и trial-вариантов. Параметры выходного файла не должны изменять сохранённый снимок коллекции.
- Разделить получение коллекции, сравнение снимков и формирование JSON/CSV. Использовать уже существующую границу ICollectionProvider; не переносить WPF в логику хранения и сравнения.
- Явно определить семантику `ownedTotal`: фактическое количество принадлежащих пользователю постоянных копий, независимо от отображения отдельных вариантов. Trial-копии учитывать отдельно.
- Сохранить названия и типы существующих полей JSON и CSV. Внутреннее хранилище снимков получает собственную версию формата, отдельную от публичного JSON.
- Для настроек премиальных карт определить единое поведение в файлах и интерфейсе. Переключение настройки не должно создавать фиктивные изменения в сохранённой коллекции.
- Не считать изменение названия карты или её локализации изменением количества копий.

Готово, когда одна и та же коллекция с разными настройками выходного файла даёт нулевую разницу, а реальное добавление или уменьшение любого варианта карты отражается точно.

## 3. Снимки по аккаунтам и миграция старых данных

Новые компоненты: разрешение идентификатора аккаунта, хранилище снимков, миграция предыдущих файлов.

Работы:

- Использовать стабильную пару `accountHi`/`accountLo` как основу идентификатора. BattleTag использовать для отображения: изменение имени не создаёт новый аккаунт.
- Хранить снимки в отдельной папке для каждого аккаунта. Для имени папки использовать хеш канонического идентификатора.
- Сохранять 64-битные идентификаторы без потери точности; отдельно проверить Windows, Swift и JavaScript-потребителей.
- Если идентификатор аккаунта ещё недоступен, показать соответствующее состояние и не сравнивать коллекцию с произвольным чужим снимком.
- Перед сравнением и импортом проверять принадлежность снимка аккаунту. Автоматически создавать первую точку сравнения только для установленного аккаунта.
- Найти прежние `last-collection-export.json` в английской и русской папках, а также доступные старые полные экспорты. Проверить структуру, сохранить оригиналы и перенести пригодные данные.
- Сделать миграцию повторяемой: повторный запуск не создаёт дубликаты и не заменяет новые снимки старыми.
- Старые файлы без идентификатора или с недостаточными данными обозначать как требующие ручного выбора либо нового полного считывания. Не восстанавливать отсутствующие количества предположениями.
- Повреждённый снимок отличать от отсутствующего: показать ошибку, предложить пригодную резервную копию или создание нового снимка, сохранить повреждённый оригинал для диагностики.

Готово, когда аккаунты A и B имеют независимые точки сравнения, переименование BattleTag сохраняет историю, а миграция старой установки не теряет доступные данные.

## 4. Надёжная запись экспорта, снимков и настроек

Новые компоненты: запись файла через временный файл, резервирование предыдущего снимка и восстановление после незавершённой операции.

Работы:

- Записывать временный файл в той же папке, закрывать и сбрасывать его на диск, затем заменять целевой файл. Предыдущий снимок сохранять в резервной копии.
- Использовать имена экспортов, исключающие столкновение двух операций в одну секунду. Не перезаписывать ранее созданный экспорт случайным совпадением имени.
- При выборе JSON и CSV сначала подготовить оба файла, затем завершить их сохранение. Продвигать точку сравнения только после успешного сохранения всех выбранных файлов.
- Не обещать общей атомарности двух файлов: при сбое между их переименованиями распознавать частичное завершение и сообщать, какие файлы уже сохранены.
- Отдельно сообщать ситуацию «экспорт сохранён, но новый снимок сравнения сохранить не удалось».
- Исключить одновременно выполняющиеся операции с одним хранилищем. Корректно обработать закрытие окна и выгрузку плагина во время экспорта.
- Применить надёжную запись к настройкам самого экспортера; не изменять остальные настройки HDT.
- Различать отсутствие доступа, занятый файл, повреждённый JSON и отсутствие данных коллекции. Пользователь получает краткое понятное сообщение; технические подробности остаются в локальном журнале.

Готово, когда сбой записи не уничтожает прежний пригодный снимок, не продвигает точку сравнения ошибочно и не отображается как успешный экспорт.

## 5. Один плагин и новый основной экран

Затрагиваемые области: `HdtCollectionExporterPlugin`, `PluginSettings`, `ExportWindow.xaml`, code-behind и `ExportWindowText`.

Работы:

- Оставить одну точку входа IPlugin со стабильным именем для настроек HDT. Локализовать меню экспортера и его окно.
- Добавить выбор языка: автоматически, русский, английский. Автоматический режим использует язык HDT, если API его предоставляет, иначе язык системы.
- Перенести настройки прежней активной языковой версии: папку экспорта, параметры, язык и размеры окна. Объединить доступ к снимкам независимо от языка.
- Для обновления подготовить скрипт установки: резервная копия прежней DLL и настроек, копирование в постоянную папку Plugins, перенос только записей этого плагина при закрытом HDT. При ручной замене DLL документировать возможную необходимость однократно включить новую запись.
- На основном экране оставить состояние коллекции, папку, режим «Полная коллекция / Изменения», формат «JSON / CSV / оба» и одну основную кнопку.
- Управление предыдущим снимком, импортом и дополнительными параметрами поместить в дополнительный раздел.
- Полностью локализовать обычные статусы и ошибки. Заменить `Baseline` понятным обозначением предыдущего снимка коллекции; убрать английский `Ready.` из русской версии.
- Сделать статус и результат операции доступными без прокрутки всего окна. Учитывать рабочую область монитора и DPI; не задавать минимальный размер больше доступного экрана.
- Сохранить управление с клавиатуры, понятный порядок фокуса, читаемый контраст и блокировку повторного запуска операции.

Готово, когда в HDT виден один плагин, смена языка не меняет аккаунт и данные, а основной сценарий проходит без поиска среди шести кнопок экспорта.

## 6. Состояние коллекции, предварительная сводка и результат

Работы:

- Различать ожидание запуска игры, ожидание чтения коллекции, готовую коллекцию, устаревшие данные и ошибку получения данных. Готовность определять по данным HDT, а не только по наличию процесса Hearthstone.
- Показывать аккаунт, время считывания, число уникальных принадлежащих карт и число постоянных копий. Не смешивать копии и строки справочника.
- Обновлять состояние без частых параллельных запросов к HDT. Ограничить повторные чтения и отменять их при выгрузке плагина.
- Перед экспортом изменений показывать число добавленных, уменьшившихся и изменившихся записей, а также изменения пыли и других поддерживаемых данных профиля.
- Сводку и файл формировать из одного подготовленного снимка. Если коллекция изменилась после предварительного просмотра, явно обновить сводку перед сохранением.
- Показывать реальные этапы операции — чтение, подготовка, сохранение — без выдуманных процентов.
- После сохранения показывать пути, время и результат; добавить «Открыть папку», «Показать файл», «Копировать путь».
- Если предыдущего снимка нет, объяснять создание первой точки сравнения и не сообщать о создании файла изменений, которого нет.

Готово, когда пользователь понимает готовность данных до нажатия кнопки, а показанные изменения соответствуют сохранённому файлу.

## 7. История снимков и сводка коллекции

Работы:

- Сохранять неизменяемый полный снимок после успешного экспорта и по команде сохранения текущей коллекции. Хранить дату, аккаунт, версию внутреннего формата и контрольную сумму.
- Разделить историю и указатель на текущую точку сравнения. Выбор старой даты не должен уничтожать более новые снимки.
- Добавить список снимков с датой и краткими показателями, выбор двух снимков одного аккаунта и экспорт их разницы в JSON/CSV.
- Восстанавливать список из пригодных файлов при повреждении индекса. Повреждённые записи обозначать явно.
- Показывать занимаемое место. Ограничение числа снимков сделать явной настройкой; по умолчанию сохранять историю без автоматического удаления.
- Добавить сводку по наборам и редкости: уникальные принадлежащие карты, число копий и разбивка по премиальным вариантам.
- Для показателя полноты набора использовать полный подходящий каталог collectible-карт HDT/HearthDb. Не выводить процент полноты только по строкам пользовательского экспорта. Правила исключения временных и специальных наборов определить и согласовать с сайтом.
- Использовать один набор данных для сводки, предварительного просмотра и экспорта. Метаданные каталога по возможности брать локально, не добавляя сетевые запросы в экспорт.

Готово, когда можно выбрать старую дату, получить воспроизводимую разницу и увидеть показатели набора, которые сходятся с полным снимком и согласованными правилами сайта.

## 8. Тесты и совместимость — на каждом этапе

Добавить `tests/HdtCollectionExporter.Tests` для .NET Framework 4.7.2 с x64-запуском. Проверять логику через ICollectionProvider и искусственные коллекции; реальные данные аккаунта не использовать как публичные fixtures. Сохранить полный MSBuild для существующего WPF-проекта; не совмещать эти изменения с миграцией всего приложения на другой runtime.

Обязательные сценарии:

- Неизменённая коллекция; добавление, уменьшение и исчезновение карты; все постоянные и trial-варианты; нулевые количества и неизвестные карты.
- Смена аккаунта, изменение BattleTag, отсутствующий идентификатор и значения идентификаторов выше безопасного диапазона JavaScript Number.
- Переключение параметров экспорта без ложных изменений коллекции.
- Повреждённый снимок, резервная копия, старая версия формата, повторная миграция и неполный legacy-файл.
- Сбой при сохранении JSON, CSV, снимка и настроек; частично завершённый экспорт; два запуска в одну секунду; повторное открытие окна после ошибки.
- Совпадение предварительной сводки с итоговым файлом; сравнение выбранных исторических снимков без изменения текущей точки сравнения.
- Согласованность сводки с количествами карт и правилами каталога.
- Старые и новые полные JSON-файлы импортируются сайтом. Файл изменений по-прежнему распознаётся как отдельный формат, который сайт не принимает вместо полной коллекции.
- CSV корректно сохраняет кириллицу, кавычки, запятые и переносы строк; существующие заголовки остаются совместимыми.
- Одна запись плагина, сохранение языка и включения после перезапуска, работа окна на небольшом экране и при увеличенном DPI.

CI должен собирать Debug/Release, запускать тесты и проверку загрузки x64 DLL, публиковать отчёты и готовые артефакты сборки. Обычный PR выполняет проверки без публикации релиза; release-процесс собирает пакет из проверенного коммита.

Swift-адаптер получает те же исправления полного снимка, разделения аккаунтов и истории. Атомарная запись в нём уже используется — её сохранить. Общие JSON-fixtures проверяют семантику обеих реализаций. Перед заявлением о поддержке новой версии нужен macOS build в совместимом HSTracker и ручная проверка меню; Windows-проверка не заменяет эту проверку.

## Порядок реализации и приёмка

1. Зафиксировать fixtures, воспроизводимую сборку и базовую CI-проверку; выпустить 1.4.2.
2. Добавить регрессионные проверки выявленных ошибок, затем реализовать полные снимки, аккаунты, миграцию и надёжную запись.
3. Реализовать одну точку входа, миграцию настройки включения, языки и новый основной экран.
4. Добавить состояние коллекции, предварительную сводку и действия с результатом; проверить импорт на сайте и согласовать Swift-адаптер; выпустить 1.5.0.
5. Добавить историю, выбор даты и сводку по наборам/редкости; выполнить проверки обеих платформ и выпустить 1.6.0.

Перед каждым выпуском: проверить чистую установку и обновление с 1.4.1, сохранить возможность отката, скачать опубликованный пакет и проверить именно его в HDT. Для финальной приёмки нужен полный цикл с запущенным Hearthstone: прочитать коллекцию, сохранить JSON/CSV и проверить разницу двух реальных снимков, полученных при обычных действиях пользователя. Проверку импорта JSON выполнять на локальной или тестовой копии сайта; публикация реальных данных аккаунта в этот план не входит.

Готовность всего плана означает, что реализованы все три выпуска, совместимость подтверждена, миграция проверена, опубликованные файлы соответствуют проверенным сборкам, а установленный плагин прошёл реальный сценарий работы с коллекцией.
